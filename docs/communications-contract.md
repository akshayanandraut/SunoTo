## Product event and template allowlist

The current packet has `notifications.enabled=false`, no service base URL, no provisioned `GRASANY_NOTIFY_SUNOTO_KEY`, and no enabled product email/SMS aliases. Identity lifecycle email (account verification, recovery, and identity security notices) belongs to Grasany ID, not SunoTo. SunoTo has no phone-number-based workflow and must not infer one from a user profile or chat content. No marketing message is authorized. A verified product-specific support identity and its acknowledgement/reply templates are mandatory before launch, but must come from the central registry packet; no address or schema is guessed here. `support.acknowledged` is recorded only as an existing-but-disabled central alias, not as an allowlisted template.

The Worker policy in `worker/src/policies/communicationsPolicy.js` rejects every unregistered template, rejects SMS until its exact regional sender and template have India DLT approval, and keeps WhatsApp disabled. Add an event only after its alias and exact merge-data schema are confirmed in the central communications registry and the affected user journey has consent/preferences behavior and contract fixtures.

The required future support journey is authenticated and in-app: create a request with product identity, tenant/user reference, category, request ID, and safe diagnostic context; keep sensitive product content in the protected in-app request record and link to it rather than copying it into email. Show the verified/enabled product support identity only after the registry confirms it. Provide in-app acknowledgement/status plus asynchronous email acknowledgement/reply handling; distinguish request acceptance from actual delivery. Support replies are operational communications, separate from marketing consent. The packet's fallback calls for a product web form protected by Turnstile and an in-product ticket reference; it also specifies five submissions per IP per hour, three per recipient per day, and no attachments. These controls, Turnstile credentials, and the operational queue owner are not provisioned, so the support form remains blocked.

## Adapter request boundary (future, registry-dependent)

For an approved event only, SunoTo may request a send through the central adapter using authenticated product identity and registry-defined product/tenant/user scope. The corrected packet specifies request `POST /api/notifications/v1/requests` with `app_id`, `event`, `template_key`, `channel`, server-resolved verified `address`, `recipient_ref`, `locale`, `idempotency_key`, `correlation_id`, and exact allowlisted `payload`. The only event currently listed is `support.requested` with disabled email template `support.acknowledged`; its exact payload is `recipient_ref`, `ticket_ref`, and `secure_status_url`. A provider-neutral signer in `worker/src/services/centralNotificationSigning.js` implements request and status headers, but only signs locally and makes no network request. Canonical bytes are `{unix_timestamp_ms}\n{uppercase_method}\n{canonical_path_without_query}\n{exact_raw_body}`; timestamp tolerance is ±300 seconds, HMAC-SHA256 lowercase hex, with `x-grasany-app-id`, `x-grasany-timestamp`, `x-grasany-signature`. The secret is absent and destination base URL is null, so no adapter call is possible. Raw credentials, email addresses, phone numbers, or case details must not be copied into browser code or logs.

Adapter acceptance means only that work was accepted for processing. A new request returns HTTP 202; an idempotent duplicate returns HTTP 200 with the original notification ID/status. Status is queried using `GET /api/notifications/v1/status?notification_id={uuid}` and signs an empty body against canonical path `/api/notifications/v1/status` (query excluded). The service base URL is still null, so neither request nor status lookup is active. Central states are `queued`, `sending`, `accepted`, `sent`, `delivered`, `failed`, `suppressed`, and `dead_letter`; persist only where a product experience requires it, and never display “delivered” from API acceptance.

Any future event must honor consent, channel preferences, quiet hours, suppression/opt-out, rate limits, locale, minimal data, and idempotency. SMS remains unavailable until both regional account readiness and the exact sender/template registration are verified; free-form and marketing SMS are prohibited. WhatsApp remains completely disabled until the user explicitly resumes it. Where a notification is optional, show a clear in-product fallback and allow the core workflow to continue; for security-critical identity or recovery flows, fail safely rather than bypass central identity delivery.
